# Spec: Test Mode

> **Estado:** DRAFT
> **Fecha:** 2026-04-19
> **Autor:** nahuel

---

## 1. Objetivo

Agregar un modo de prueba (`--test-mode`) que intercepta la resolucion de destinatarios en `resolve_delivery()` y redirige toda la entrega (email + WhatsApp) hacia un unico contacto seguro ("Nahuel Aguirre"), permitiendo ejercitar el pipeline completo (generacion xlsx, captura de imagen, envio email, envio WhatsApp) sin spammear destinatarios reales.

---

## 2. Contexto

El pipeline de entrega actual resuelve el mapa `enviar_a` de cada reporte en emails/telefonos reales via `resolve_delivery()`. Ejecutar los configs de produccion implica enviar mensajes a supervisores y directivos. Los workarounds actuales (editar `contactos.json` manualmente, comentar `enviar_a`) son propensos a errores y riesgo de commits accidentales. El chokepoint de contacto ya esta centralizado en `resolve_delivery()` (lineas 45-119 de `src/config/resolver.py`), lo que hace que la feature sea un cambio de 3-5 lineas en el core con plumbing en el CLI.

Contacto de prueba en `configs/contactos.json`:
```json
"Nahuel Aguirre": {
    "email": "naguirre@danielmanzur.com",
    "telefono": "5493876008331"
}
```
Nahuel no tiene `whatsapp_grupo`; el fallback existente (`whatsapp_grupo` -> `telefono`) ya cubre este caso.

## 3. Requisitos Funcionales

### 3.1 Activacion CLI

- **RF-001**: Cuando el usuario pasa `--test-mode` al parser raiz de argparse, el sistema debe activar test mode independientemente de subcomandos o configs presentes.

- **RF-002**: Cuando la variable de entorno `INFORMES_TEST_MODE` tiene valor `"1"`, `"true"`, `"True"` o `"yes"` y el flag CLI no esta presente, el sistema debe activar test mode.

- **RF-003**: Cuando tanto `--test-mode` como `INFORMES_TEST_MODE` estan presentes, el sistema debe activar test mode (el flag CLI tiene precedencia logica; el resultado efectivo es identico porque ambos activan el mismo modo).

### 3.2 Banner de inicio

- **RF-010**: Cuando test mode esta activo, el sistema debe imprimir exactamente una vez al stdout, antes de procesar cualquier reporte, la cadena:
  `⚠️ TEST MODE ACTIVO — delivery redirected to Nahuel Aguirre`

- **RF-011**: Cuando test mode esta inactivo, el sistema no debe imprimir ningun banner relacionado con test mode.

### 3.3 Logica de colapso (core)

- **RF-020**: Cuando test mode esta activo y `enviar_a` tiene N entradas (N >= 1) con distintos valores de `via`, el sistema debe reemplazar `enviar_a` por exactamente una entrada `{"Nahuel Aguirre": DeliveryTarget(via=<union ordenada de todos los via>)}` antes de iterar los contactos.

- **RF-021**: Cuando test mode esta activo y `enviar_a` tiene una sola entrada con `via=["email"]` y `whatsapp=False`, el sistema debe colapsar a `{"Nahuel Aguirre": DeliveryTarget(via=["email"])}` (no agrega canales que no existian).

- **RF-022**: Cuando test mode esta activo y `enviar_a` es `None` o `{}`, el sistema debe dejar el resultado como `{}` sin crear ninguna entrada sintetica (no hay nada que redirigir).

- **RF-023**: Cuando test mode esta activo, el colapso debe ocurrir dentro de `resolve_delivery()` antes del loop `for contact_name, target in enviar_a.items()`, de modo que el resto de la logica de resolucion de contactos permanezca sin cambios.

### 3.4 Interaccion con gates globales de canal

- **RF-030**: Cuando test mode esta activo y el parametro `enviar_email=False` se pasa a `resolve_delivery()`, el sistema no debe incluir email en los destinatarios de Nahuel (el gate sigue activo).

- **RF-031**: Cuando test mode esta activo y el parametro `enviar_whatsapp=False` se pasa a `resolve_delivery()`, el sistema no debe incluir WhatsApp en los targets de Nahuel (el gate sigue activo).

- **RF-032**: Cuando test mode esta activo y los gates estan habilitados, los valores de `email`/`whatsapp` presentes en los `via` colapsados de `enviar_a` determinan que canales se activan, independientemente de cuantos contactos originales existian.

### 3.5 Resolucion del contacto de prueba

- **RF-040**: Cuando test mode esta activo y el canal email esta habilitado, el sistema debe agregar `"naguirre@danielmanzur.com"` a la lista `destinatarios` del `EmailConfig` resultante.

- **RF-041**: Cuando test mode esta activo, el canal WhatsApp esta habilitado, y el contacto "Nahuel Aguirre" no tiene campo `whatsapp_grupo`, el sistema debe agregar el valor de `telefono` (`"5493876008331"`) a la lista `grupos` del `WhatsAppConfig` resultante.

- **RF-042**: Si en el futuro el contacto "Nahuel Aguirre" recibe un campo `whatsapp_grupo` en `contactos.json`, el sistema debe usar ese valor en lugar de `telefono` para WhatsApp (comportamiento heredado del fallback existente, sin cambio de logica).

### 3.6 Plumbing del parametro

- **RF-050**: El parametro `test_mode: bool = False` debe agregarse a la firma de `resolve_delivery()` como ultimo keyword argument con default `False`.

- **RF-051**: La funcion `_run_reportes()` debe aceptar `test_mode: bool = False` y forwarded a cada llamada a `resolve_delivery()`.

- **RF-052**: La funcion `_run_report_config()` debe aceptar `test_mode: bool = False` y forwarded a `_run_reportes()`.

- **RF-053**: La funcion `main()` debe resolver `test_mode` (flag CLI OR env var), imprimr el banner si activo, y pasar el valor a todos los call sites de `_run_report_config()` y `_run_config_dir()`.

### 3.7 Guard para paths legacy

- **RF-060**: Cuando test mode esta activo y se invoca `_cmd_ventas_legacy()` o `_cmd_resumen_legacy()`, el sistema debe emitir un log `WARNING` con el mensaje `"test-mode has no effect on legacy path: {nombre_funcion}"` y continuar la ejecucion sin redirigir destinatarios.

## 4. Requisitos No Funcionales

- **RNF-001**: El colapso en `resolve_delivery()` no debe agregar imports externos ni dependencias nuevas.
- **RNF-002**: El banner debe imprimirse en stdout (no stderr) usando `print(..., flush=True)`.
- **RNF-003**: La logica de colapso debe ser unit-testable sin base de datos ni red: basta con un `ReportEntry` sintetico y un `contactos` dict en memoria.
- **RNF-004**: El flag `--test-mode` debe aparecer en el `--help` del parser raiz con descripcion: `"Redirect all delivery to Nahuel Aguirre for safe end-to-end testing"`.

## 5. Diseno Tecnico

### 5.1 Modelo de Datos

No se requieren cambios de base de datos ni nuevos modelos Pydantic. El tipo `DeliveryTarget` existente en `src/config/models.py` (campo `via: list[Literal["email", "email_cc", "whatsapp"]]`) es suficiente para construir la entrada sintetica.

Contacto de prueba (ya existe, sin cambios requeridos):
```json
// configs/contactos.json
"Nahuel Aguirre": {
    "email": "naguirre@danielmanzur.com",
    "telefono": "5493876008331"
}
```

### 5.2 Arquitectura

El cambio toca cuatro niveles en una cadena vertical:

```
main()
  └─> _run_report_config(config_path, contactos_path, test_mode)
        └─> _run_reportes(report_config, contactos, test_mode)
              └─> resolve_delivery(report, contactos, enviar_email, enviar_whatsapp, test_mode)
                    └─> [colapso] enviar_a = {"Nahuel Aguirre": DeliveryTarget(via=union)}
                          └─> [loop existente sin cambios]
```

El banner se imprime UNA VEZ en `main()`, no en las sub-funciones, para evitar spam en runs multi-config.

`_run_config_dir()` llama a `_run_report_config()` en un loop; debe recibir y propagar `test_mode` tambien.

### 5.3 API / Interfaz

#### Firma modificada de `resolve_delivery()`

```python
def resolve_delivery(
    report: ReportEntry,
    contactos: dict[str, ContactInfo],
    enviar_email: bool = True,
    enviar_whatsapp: bool = True,
    test_mode: bool = False,          # NUEVO
) -> DeliveryConfig | None:
```

#### Bloque de colapso (insertar antes del loop en linea 65)

```python
enviar_a: dict[str, DeliveryTarget] = report.enviar_a or {}
if test_mode and enviar_a:
    all_via: set[str] = set()
    for target in enviar_a.values():
        all_via.update(target.via)
    enviar_a = {"Nahuel Aguirre": DeliveryTarget(via=sorted(all_via))}
# luego iterar `enviar_a` (local) en lugar de `report.enviar_a`
```

#### Resolucion de `test_mode` en `main()`

```python
test_mode = bool(args.test_mode) or os.getenv("INFORMES_TEST_MODE") in {
    "1", "true", "True", "yes"
}
if test_mode:
    print("⚠️ TEST MODE ACTIVO — delivery redirected to Nahuel Aguirre", flush=True)
```

#### Flag CLI (root parser)

```python
parser.add_argument(
    "--test-mode",
    action="store_true",
    default=False,
    help="Redirect all delivery to Nahuel Aguirre for safe end-to-end testing",
)
```

## 6. Edge Cases y Constraints

| Caso | Comportamiento esperado |
|------|------------------------|
| `enviar_a = {}` | No se crea entrada sintetica; `resolve_delivery` retorna `None` si tampoco hay captures |
| `enviar_a = None` | Idem: sin redireccion |
| Unico contact con `via=["email_cc"]` | Union produce `["email_cc"]`; Nahuel recibe email como CC, no como destinatario principal |
| `enviar_email=False` + test_mode | Email suprimido aunque `via` incluya "email" |
| `enviar_whatsapp=False` + test_mode | WhatsApp suprimido aunque `via` incluya "whatsapp" |
| Flag CLI + env var ambos seteados | test_mode = True (OR logico; comportamiento identico) |
| `--test-mode` + subcomando legacy (`ventas` sin `--config` nuevo) | WARNING log emitido; pipeline continua sin redireccion |
| `--test-mode` + `--config-dir` con 5 configs | Banner impreso una vez; todos los reportes redirigen a Nahuel |
| Contact "Nahuel Aguirre" no existe en contactos.json | `resolve_delivery` loguea WARNING "Contact not found, skipping" igual que cualquier otro contacto faltante |
| `via` con duplicados en distintas entradas (`["email", "email"]`) | `set.update` deduplica automaticamente; `sorted()` garantiza orden deterministico |

- [ ] **Escenario-5 (Legacy bypass)**: `python main.py ventas --test-mode --desde ... --hasta ...` (subcomando legacy) → WARNING logueado, ningun redirect → valida RF-060

## 9. Boundaries (Lo que NO hacer)

- NO modificar `_cmd_ventas_legacy` ni `_cmd_resumen_legacy` para que soporten redireccion (solo emitir el WARNING).
- NO agregar un segundo contacto de prueba ni leer `INFORMES_TEST_CONTACT` env var (fuera de scope v1).
- NO suprimir capturas de imagen ni ningun otro paso del pipeline en test mode (todo el pipeline se ejercita).
- NO crear un `contactos_test.json` separado.
- NO modificar `configs/contactos.json` como parte de esta implementacion.
- NO tocar `src/delivery/pipeline.py`, `src/delivery/steps.py` ni ningun servicio especifico de reporte.
- NO agregar el flag `--test-mode` a los subparsers individuales (solo el root parser).
